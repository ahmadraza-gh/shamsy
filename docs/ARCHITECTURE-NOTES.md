# Architecture and domain notes

- Catalogue prices are authoritative on the server/database. The client submits `productId`, never an authoritative price. PostgreSQL loads `products.price_cents` when a product first enters an order and preserves that snapshot through later draft edits.
- USD money is stored and calculated as integer cents (`bigint` in PostgreSQL). No stored monetary field uses floating point.
- Each order line snapshots its catalogue price in `order_lines.unit_price_cents`; later catalogue changes do not change that line.
- Each order snapshots its USD→SDG rate in `orders.exchange_rate`; historical totals never depend on the current setting.
- Line values/totals are generated by PostgreSQL. Order totals are recomputed transactionally on save and again immediately before confirmation.
- Discount bands use exact integer inequalities, not rounded display percentages. Values above 5% require persisted approval for that exact line.
- The owner approval function determines the current actor with `auth.uid()` and verifies `profiles.role = 'owner'`. An adviser cannot approve by forging a request or approver ID.
- Confirmed orders are read-only at both the application and database-trigger layers.

## Saving versus approval ambiguity

The source language says saving is blocked until owner approval, but an owner needs a persisted entity to review. The application permits a `draft`/`pending_approval` record to be stored; **confirmation remains impossible** until every line above 5% has owner approval. Editing a pending draft replaces its lines and clears prior approvals, preventing stale approval reuse.

That interpretation follows the brief's explicit suggested resolution. A production team should still confirm the intended terminology and transition design with the product owner.

## Deliberate product choices

- Whole-SDG results use integer half-up rounding when the cents/rate product is not evenly divisible by 100. The mandatory examples are exact.
- The same product can appear only once in an order, preventing duplicate-line discount threshold splitting.
- This is a clean standalone Next.js repository, organized by feature so it can move into an Nx `apps/web` package later.
- The service-role key is needed only for protected local/CI test-user provisioning and disposable integration tests that verify trigger-level immutability; it is never used by browser or deployed runtime code.

For production, add a stronger append-only audit/event trail, ledger patterns where applicable, organization/tenant IDs, idempotency, explicit transaction-boundary review, concurrency versions, comprehensive RLS/concurrency/browser E2E coverage, offline/retry behavior, observability, backups, RTL/i18n architecture, dealer isolation, and structured audit metadata.
